# 性能

この手引きは、データが増えたときに、データをどこに置き、どの
設定に気を配ればよいかを決めるためのものです。文書とデータセットが
どれだけの量を扱えるか、多くの地物をまとめて書き込む方法、頂点の
多い線を編集できる状態に保つ仕組み、プレビューのために描画を縮める
方法を説明し、
最後に、測った例、パッケージの大きさ、自分のデータで測る方法を
紹介します。

## データの置き場所

| データ | 置き場所 | 理由 |
| --- | --- | --- |
| 利用者が描いて編集するもの | 文書 | 編集、イベント、書き出し |
| 大きな参照データ | データセット | 編集の負担が無い |
| 一度に読み込めないほど大きなデータ | provider を使うデータセット | 範囲ごとに読む |
| 100 万行の表 | 表 (`table`) で渡すデータセット | 行ごとのオブジェクトが要らない |

データセットは、数万件の地物を扱う前提で作っています。
graduated のスタイル規則を付けた 5 万件の多角形のデータセット
を、GPU のある機械でパンやズームしたところ、120 Hz の画面の
描く 1 回の時間に収まりました。provider を使えば、見えている範囲の
地物だけを持つので、元のデータの総量は影響しません。

数十万行の表は、型付き配列の列の表 (`table`) にして、Worker で
読んで下ごしらえしてから渡すのが最適です。行は GPU の配列に直接
詰められ、本体のスレッドは行ごとのオブジェクトを作りません
([大量のデータを表示する](large-data.ja.md))。

文書の地物はどれも、編集、当たり判定、イベント、書き出しの対象に
なります。測った場面の例を後に載せています。文書に数千件を超える
地物を置くつもりなら、対象の端末で計測のページ (後述) を使って
測ってください。

大きなデータのうち一部の地物だけを編集するなら、データは
データセットに置き、編集する行だけを `tx.features.create` で
文書へ写します。[大量のデータを表示する](large-data.ja.md) を
参照してください。

## 最小の設定

```ts
import { createDraw } from '@sakuzu/maplibre-gl-draw';

const draw = createDraw(map, {
  rendering: {
    cacheGeometry: true, // 既定
    timeSlicing: true, // 既定
  },
});
```

画面に表示するなら、どちらも既定のままで適切です。変えるのは、
以下で説明する場合だけです。作るときにも、後から
`draw.options.update` でも変えられます。

## 多くの地物を書き込む

`draw.write` は、書く地物の数によらず 1 回ごとに 1 つの確定になり、
イベントも届きます。多くの地物を作る、変える、消すときは、`tx` の 1 つの
書き込みに渡します。`create` は地物の配列を受け取り、`update`、`delete`、
`translate`、`rotate`、`scale`、`place` は ID、絞り込み、選択、
`{ all: true }` を受け取ります。描画と `change` は全体に対して 1 回で
済みます。

<!-- docs-check:
declare const inputs: import('@sakuzu/maplibre-gl-draw').FeatureInput[];
declare const hiddenIds: string[];
-->

```ts
// 1 つの取引の種類の違う書き込みは 1 つの確定になる
await draw.write(async (tx) => {
  await tx.features.create(inputs);
  await tx.features.delete(hiddenIds);
  await tx.layers.update(layerId, { opacity: 0.5 });
});
```

GeoJSON のファイルは `draw.open` か `tx.import` で 1 度に読めます。
これもすべての地物を 1 つの確定で書き込みます
([保存と読み込み](save-load.ja.md))。

## 形を持ち続ける

変わらない地物の形は、レイヤーごとに GPU の上に持ち続けるので、
地図を動かしても作り直しません。データセットは地図の区画ごとに
形を持ち、見えている区画だけを描きます。`cacheGeometry: false`
にすると、描くたびに文書の形を作り直します。描かれる絵は同じ
なので、描画の問題を調べるときに、持ち続けている形が原因で
ないことを確かめるためだけに使ってください。

描く 1 回に収まらない仕事は、後に描く回に分けて進めます。その
ため、タイルが順に届くように絵が埋まっていく間も、ページは止まり
ません。分けて進めるのは、データセットの形を作る仕事 (描く 1 回
ごとに時間の上限があります)、データセットの中の頂点がとても多い
多角形 (1 万を超えるもの) の塗り (輪郭が先に表示され、塗りは
仕事が終わってから表示されます)、地形の準備です。

## 絵を取り出すための完全な描画

印刷、サムネイル、書き出しのように、描いて絵を読み出す地図では
`timeSlicing: false` にしてください。描く 1 回がどれも完全になります。
上の仕事を、その 1 回がどれだけ長くなっても、それを必要とする 1 回の
中で終えます。操作する地図では既定のままにしてください。

描く 1 回が完全でも、絵が完全とは限りません。地図のタイルと DEM は
非同期に届きますし、描く 1 回の中では終えられない仕事もあります
(provider の応答や、何回かの描画にかけてデータを用意するオーバーレイの
描画)。そうした仕事が残っているかどうかは `draw.hasPendingWork()`
でわかります。地図は、このライブラリーが直前の 1 回で次の描画を
求めていても `idle` を発火するので、`idle` を待ったあと、描いた
後に `hasPendingWork()` が false になるまで待ちます。

```ts
async function whenPictureComplete(): Promise<void> {
  map.triggerRepaint();
  await map.once('idle');
  while (draw.hasPendingWork()) await map.once('render');
}
```

データセットの点の衝突による間引きには、何もいりません。描く 1 回が、
描くときのズームから描く点を決めます。

画面に見えているままの地図の絵には、2 つ目の地図はいりません。
`draw.captureImage` は、地図が次に描く 1 回で、選択とその
ハンドルと描いている途中の形を除いて絵を取り、求めた大きさにします
(形の違う大きさでは、地図で覆って真ん中で切ります)。絵の文書は
書かれたままの形で、ドラッグや下書きが動かしている物は動かす前の
位置に写ります。かかるのは描く 1 回なので、もう 1 度描くには大きすぎる
文書のサムネイルに向きます。

```ts
const thumbnail = await draw.captureImage({
  width: 320,
  height: 200,
  type: 'image/webp',
  quality: 0.8,
});
```

## 端末の上限に対するメモリー

ブラウザーは、端末がそのページに使わせるより多くのメモリーを取る
ページを止めます。スマホはデスクトップより少ないです。
`draw.memory.get()` は、ページで描いている文書が取るメモリーを、端末の
上限と並べて返します。上限は iPhone で 400 MiB、iPad で 500 MiB、
ほかで 1 GiB で、`draw.memory.setLimit` で決めることもできます。
ページの draw インスタンスを全部数えます。印刷する 2 つ目の
インスタンスも、文書の代わりに見せている文書も入ります。
`gpuBytes` は描画が GPU に割り当てた量で、`jsBytes` は地物とその
位置の数からの見積もりです (ページのヒープは、どのブラウザーでも
わかるわけではありません)。基図とページのほかの部分は入りません。

行の外の GPU の量、つまり文書の大きさに比例しない分には、instance ごとの上限が
あります。`rendering.gpuLimitBytes` で渡し、省くと 64 MB です。ライブラリーと
拡張はこの値を一緒に読みます。`draw.debug.gpu()` は `bytes` と `rowBytes` を
答えます。地物の数に比例する分 (`gpu.rows`) はこの上限の外で、端末に残る量までです。
拡張はこの値の割合 (`gpuShare`) を持ち、それを超える割り当ては断られます
([プラグインが GPU に持つもの](custom-types.ja.md#プラグインが-gpu-に持つもの))。
`draw.options.update` で変えるとすぐに従います。持っているものは解放されず、
次の割り当てが断られます。端末がどれだけ空けられるかはライブラリーには分からない
ので、利用者の端末に合わせた値を渡してください。

`draw.memory.estimate` は、ある大きさの文書が、インスタンスの Store が
地物を持つ形で取る量を返します。上限を超えるもの (開く地図、印刷、
見る版) を、始める前に止められます。

```ts
const now = draw.memory.get();
const added = draw.memory.estimate({ features: 120_000, positions: 700_000 });
if (now.bytes + added.bytes > now.limitBytes) {
  // この端末には大きすぎることを伝え、開かない
}
```

インスタンスは何も断りません。何を止め、何を伝えるかはページが
決めます。

## 頂点の多い線

GPS の軌跡のように頂点が数千ある線は、そのままでは頂点の
ハンドルで覆われてしまいます。そこで、選択した地物の頂点と中点
のハンドルが 400 を超えると、一部だけを表示します。

- 頂点は、直前に表示した頂点から画面上で 14 px 以上離れていれば
  表示します。各線と各リングの最初の頂点と、開いた線の最後の
  頂点は常に表示します
- 中点は、両端の頂点が表示されていて、画面上で 32 px 以上の長さ
  がある辺にだけ表示します
- 掴めるのは表示されているハンドルだけです。線のほかの所を掴む
  と、地物全体が動きます
- 表示するハンドルの組は、カメラが 150 ms 止まったときに作り
  直します。頂点を追加したり削除したりしたときは、すぐに作り
  直します。ズームインすると表示される頂点が増え、最終的には
  すべての頂点が表示されます
- 座標は変えません。吸着は、これまでどおりすべての頂点と辺
  を使います

ハンドルがそれより少ない地物には、何も影響はありません。

## 描画の大きさを変える

線の太さ、点の大きさ、縁取りは CSS ピクセルで指定し、物理
ピクセルで描きます。その比は地図の `getPixelRatio()` の値で、
`rendering.pixelRatio` を指定したときはその値です。
`pixelRatio` を指定するのは、地図とは違う比で描きたいときだけに
してください。

`rendering.renderScale` は、その比に掛ける係数です。CSS の変形
などで地図を拡大や縮小して見せるときに使います。ページの
プレビューのように地図を 1/k の大きさで見せるときは、基図は
カメラと一緒に縮むので、`renderScale` を 1/k にして、この
ライブラリーが描くピクセルの大きさも合わせて縮めます。位置と、
メートルで指定した大きさは変わりません。

```ts
// 地図を半分の大きさで見せる
draw.options.update({ rendering: { renderScale: 0.5 } });
// 元に戻す
draw.options.update({ rendering: { renderScale: 1 } });
```

正の数でない値を渡すと、コード `invalid-input` の `DrawError` を
投げ、何も変えません。描画はすぐに追随します。すでにズームに
応じて大きさが変わるもの (基準のズームで描いた線) には、重ねて
掛けません。自分で書いたオーバーレイや描画器は、係数を含めた
その時点の比をコンテキストから読みます。

```ts
draw.extensions.overlays.add({
  name: 'outline',
  draw(ctx) {
    const widthInDevicePixels = 2 * ctx.screen.pixelRatio;
    // その幅で描く
  },
});
```

## 測った例

架空の街の 208,073 件の編集できる地物を、1 度に文書に読み込みました。
多角形 174,435 件 (建物と公園)、線 24,328 件 (道)、点 9,310 件 (場所) で、
レイヤーのスタイル規則で塗り分けています。README の最後の画像がこの場面
です。

測ったのは Apple M3 Max の上の headless Chromium 151 で、ANGLE の Metal の
バックエンドにより GPU で描いています。地図は 1280 × 760 CSS ピクセル、
画素の比は 2 です。読み込みとパンは 4 回測りました。

- 208,073 件を文書に読むのに 0.64〜0.66 秒かかりました
- 地図を 10 秒間パン、ズーム、回転したときの描く 1 回は、中央値が
  8.4 ms、90 パーセンタイルが 13 ms、いちばん遅いもので 19 ms でした

クリックと矢印キーは、入力のイベントから、変化を描いた次の 1 回
までを 3 回測りました。

- 地物をクリックしてから選択が描かれるまでは約 60 ms でした (20 回ずつの
  中央値が 61、65、66 ms で、全体では 47〜91 ms)
- 選んだ地物を矢印キーで動かすと、キーを押してから約 13 ms で描かれ
  ました (6〜14 ms)

地物を 2 倍 (410,772 件、1 回) にすると、読むのに 1.3 秒かかりました。端末が違えば結果も変わるので、次の節の方法で測って
ください。

## パッケージの大きさ

パッケージはバンドルしていない ES モジュールで、バンドラーは import
したものだけを含めます。メインのエントリーのすべてを minify すると約
600 kB (gzip で約 160 kB) です。geometry のサブパスだけなら約 40 kB
(gzip で約 13 kB) です。

## 自分のデータで測る

リポジトリーには、貢献者向けの計測のページが 2 つあります。
1 つはデータセットの上で、もう 1 つは `n` 件の地物を
読み込んだ文書の上でパンとズームを行い、どちらも描く 1 回の
時間を表示します。動かし方と URL の引数は
[bench/README.md](../../bench/README.md) で説明しています。
数値は GPU とブラウザーによって変わるので、利用者が使う端末で
測ってください。
